## 1. 概述

### 1.1 问题陈述

游戏的核心数值系统和功能框架已经完整，但"情绪节奏"严重不足——玩家在关键时刻缺乏与事件强度匹配的情绪反馈。具体问题：

| # | 问题 | 严重度 | 现状分析 |
|---|------|--------|---------|
| 1 | **战斗飘字单调** | 🟡 严重 | `battle-animations-canvas.js` 已有基础飘字机制（`_floatTexts` 数组 + `_drawFloatTexts` 方法），但仅区分普攻/暴击/技能三种颜色，无 MISS/闪避表现，无终极技能特殊演出，无屏幕震动反馈，同时飘字仅通过 `Math.random() * 20` 的随机 X 偏移防重叠，效果有限 |
| 2 | **抽卡反馈无差异** | 🔴 致命 | `recruit-panel.js` 对所有品质武将使用相同的静态 HTML 渲染（`_renderResultCard` / `_renderSingleResult`），白色兵和橙色传说的展示差异仅为边框颜色和一个 `box-shadow`；`CelebrationOverlay` 虽在 `hero:added` 事件中对紫色及以上武将弹出庆祝层，但与招募流程脱节，无递进式演出 |
| 3 | **离线收益无趣味** | 🟡 严重 | `main.js` 的 `_showOfflineRewards()` 使用 Modal 静态展示金币/经验数字，阈值为 60 秒，无动画、无人格化叙事、无惊喜感。收益发放在弹窗之前就已完成（`ResourceManager.add` 先于 `Modal.show`），点击"收下！"仅关闭弹窗 |

### 1.2 核心玩家价值

> **让每一个关键时刻都有与之匹配的情绪峰值——小事有小反馈，大事有大仪式。**

- 💥 **战斗沉浸感**：实时飘字让玩家"看懂"战斗，暴击/终极的视觉强化制造微小的兴奋峰值
- ✨ **抽卡仪式感**：品质越高的武将需要越隆重的"登场仪式"，Q5 武将获得与其稀有度匹配的情绪高潮
- 🎁 **回归惊喜感**：每次打开游戏都有一份"武将们的生活报告"，制造温馨、幽默的回归动力

### 1.3 目标用户

所有活跃玩家。三个子功能分别覆盖：
- **战斗飘字**：日常推图/挂机观战的玩家（最高频场景）
- **抽卡演出**：每次消费玉璧抽卡的玩家（中频，每次都要"值回票价"）
- **离线报告**：每日回归游戏的玩家（低频但首次印象关键）

### 1.4 设计原则

1. **频率匹配强度**：高频反馈（飘字）要轻量不抢眼，低频反馈（Q5 演出）要隆重炸裂
2. **可跳过不可跳过看**：所有演出必须可跳过，但默认展示要让人"舍不得跳"
3. **不阻塞游戏循环**：所有动画/演出期间 `game:tick` 继续运行，不影响挂机收益
4. **增量叠加，不重构**：在现有 Canvas 飘字系统、EventBus 事件、Modal/OverlayPanel 基础上增强，不改变底层架构
5. **幽默基调一致**：所有文案延续"天道系统"的吐槽风格和武将现代穿越人设

### 1.5 成功指标（KPI）

| 指标 | 当前值 | 目标值 | 衡量方式 |
|------|--------|--------|---------|
| 战斗中可见反馈类型数 | 3（普攻白/暴击金/技能蓝） | ≥ 7（+治疗绿/MISS灰/终极金+震屏/技能名称） | 计数飘字 `_floatTexts` 中的 `type` 种类 |
| 抽卡演出差异化级别 | 1（所有品质相同展示） | 4（Q1-Q2/Q3/Q4/Q5 四档） | 肉眼验收各品质演出差异 |
| Q5 武将获得时的情绪峰值 | 与 Q1 相同（仅 Toast 通知） | "天道系统异常"完整演出（≥3 秒） | 验收演出序列完整性 |
| 离线回归的趣味性 | 0（纯数字 Modal） | 有武将个性化活动描述 + 信封动画 | 验收报告中武将描述数量 |
| 飘字重叠率 | 高（仅 ±10px 随机偏移） | 低（分层错开 + 延迟生成） | 目视同时 3+ 飘字时的可读性 |

## 2. 子功能 A：战斗飘字系统增强

> 核心目标：在现有 Canvas 飘字基础上，将飘字分为 7 种类型，各有独立的视觉风格，同时优化多飘字防重叠机制。

### 2.1 现状分析

当前 `BattleAnimations` 中的飘字实现：
- `playAttack()` 生成伤害飘字：普攻用 `COLORS.damage`（红），暴击用 `COLORS.crit`（金）+ 前缀"暴击"
- `playSkill()` 生成技能飘字：治疗用 `COLORS.heal`（绿），减益用 `COLORS.buff`（紫），伤害用 `COLORS.skill`（蓝）
- `playDeath()` 生成"击败"灰色飘字
- 所有飘字的数据结构为 `{ text, x, y, color, font, life, maxLife }`
- 飘字在 `_update(dt)` 中以 `30 * dt` 像素/秒的速度向上移动，生命值归零后移除
- 防重叠仅通过 `(Math.random() - 0.5) * 20` 随机 X 偏移

**缺失项**：
- 无 MISS/闪避飘字（当前 `affixDodge` 属性存在于战斗单位数据中，但闪避时无视觉反馈）
- 暴击无闪烁/缩放动画（仅字号从 11px → 14px）
- 技能飘字不显示技能名称
- 终极技能无特殊飘字和屏幕震动
- 无飘字类型（type）字段，无法区分处理

### US-A1：飘字类型扩展

**作为**观看战斗的玩家
**我想要**不同类型的战斗事件用视觉差异明显的飘字呈现
**以便于**我能一眼区分普攻、暴击、技能、治疗、闪避，读懂战斗中发生了什么

**详细描述**：

扩展 `_floatTexts` 中每条飘字的数据结构，新增 `type` 字段以驱动不同的渲染风格：

| 类型 | 触发时机 | 文本格式 | 颜色 | 字号 | 附加效果 |
|------|---------|---------|------|------|---------|
| `normal` | 普通攻击命中 | `-{damage}` | 白色 `#e8dcc8` | 小号 (11px) | 无 |
| `crit` | 暴击命中 | `-{damage} 暴击!` | 红色 `#e84545` | 大号 (16px) | 文字缩放脉冲（先放大再缩回） |
| `heal` | 治疗效果 | `+{value} ✨` | 绿色 `#5d8a48` | 中号 (12px) | 无 |
| `skill` | 技能伤害 | `-{damage} [{技能名}]` | 金色 `#d4a849` | 中号 (13px) | 无 |
| `ultimate` | 终极技能伤害 | `-{damage} [{终极名}]` | 亮金色 `#ffd700` | 超大号 (20px) | 屏幕震动 + 字号脉冲 |
| `miss` | 闪避/未命中 | `MISS` | 灰色 `#666` | 中号 (12px) | 向斜上方飘出（非正上方） |
| `buff` | 增益/减益效果 | `{buff名称}` | 紫色 `#8b5ea8` | 小号 (10px) | 无 |

**验收标准**：

| # | 标准 | WHEN / THEN |
|---|------|-------------|
| A1-1 | 普通伤害飘字 | WHEN 武将造成普通伤害 THEN 目标头顶显示白色小号伤害数字，向上飘散约 1 秒后淡出消失 |
| A1-2 | 暴击伤害飘字 | WHEN 武将造成暴击伤害 THEN 显示红色大号数字并附带"暴击!"文字，文字有明显的缩放脉冲效果（先放大后缩回） |
| A1-3 | 治疗飘字 | WHEN 武将被治疗 THEN 显示绿色数字并附带 ✨ 图标 |
| A1-4 | 技能伤害飘字 | WHEN 武将使用技能造成伤害 THEN 显示金色数字并附带技能名称（如"锦囊快递 -245"） |
| A1-5 | 终极技能飘字 | WHEN 武将释放终极技能 THEN 显示超大号亮金色数字和终极技能名称，同时 Canvas 画面产生短暂震动效果 |
| A1-6 | 闪避飘字 | WHEN 武将闪避了攻击 THEN 目标头顶显示灰色"MISS"文字，向斜上方飘出 |
| A1-7 | 飘字淡出 | WHEN 飘字生命周期结束 THEN 飘字平滑淡出（globalAlpha 从 1 线性降到 0），非突然消失 |

> 📐 `@numerical-designer`：飘字持续时间（建议普通 0.8s、暴击 1.2s、终极 1.5s）、屏幕震动幅度（建议 2-4px 持续 0.3s），需在不影响可读性的前提下调优。

### US-A2：飘字防重叠机制

**作为**观看群体战斗（3v3 或更多）的玩家
**我想要**同一时间出现的多条飘字不互相重叠遮挡
**以便于**我能看清每一条飘字的内容

**详细描述**：

当前同一单位短时间内产生多条飘字时，仅有 ±10px 的随机 X 偏移，导致文字高度重合无法阅读。需要改进防重叠策略：

- **垂直分层**：同一单位的飘字按生成顺序在 Y 轴方向错开（每条间隔 16px）
- **X 方向散射**：在现有随机基础上，根据飘字序号向左右交替偏移
- **延迟生成**：若同一帧产生多条飘字，逐条延迟 100-150ms 生成，制造"连珠"效果
- **密度限制**：同一单位同时最多显示 4 条飘字，超出的等前面的消失后再显示

**验收标准**：

| # | 标准 | WHEN / THEN |
|---|------|-------------|
| A2-1 | 多飘字不重叠 | WHEN 同一单位在 1 秒内受到 3 次以上伤害 THEN 所有飘字内容均可辨认，无完全重叠遮挡 |
| A2-2 | 连珠效果 | WHEN 全体攻击技能同时命中多个目标 THEN 各目标的飘字有视觉上的先后顺序（非同时弹出），呈现"噼里啪啦"的连珠感 |
| A2-3 | 密度可控 | WHEN 高速战斗（4x 加速）中大量飘字产生 THEN 画面不因飘字过多而变成"数字汤"，保持整体可读性 |

### US-A3：屏幕震动效果

**作为**看到武将释放终极技能的玩家
**我想要**屏幕产生一次短暂震动
**以便于**感受到终极技能的冲击力和重量感

**详细描述**：

在 Canvas 的 `_draw()` 方法中，当存在活跃的震动状态时，对整个绘制偏移 `ctx.translate(shakeX, shakeY)` 进行微小随机偏移。震动数据结构：`{ duration, intensity, elapsed }`。

触发条件：
- 终极技能命中时触发（通过已有的 EventBus `battle:tick` 事件链传导）

**验收标准**：

| # | 标准 | WHEN / THEN |
|---|------|-------------|
| A3-1 | 终极震屏 | WHEN 任意武将释放终极技能并命中 THEN Canvas 画面产生短暂震动（肉眼可感知的 2-4px 偏移，持续约 0.3 秒），随后恢复平稳 |
| A3-2 | 不影响操作 | WHEN 屏幕震动期间 THEN 不影响战斗按钮的点击交互（震动仅作用于 Canvas 内部绘制，不影响 DOM 布局） |

### US-A4：连杀反馈飘字

**作为**观看战斗中己方连续击杀敌人的玩家
**我想要**看到"三杀""五杀""超神"之类的连杀提示
**以便于**感受到战斗的连续爽快感和团队碾压的成就感

**详细描述**：

在同一场战斗中，跟踪己方连续击杀敌人的计数。当连杀数达到阈值时，在 Canvas 画布中央弹出对应的连杀飘字：

| 连杀数 | 展示文案 | 视觉风格 |
|--------|---------|---------|
| 3 | 🔥 三杀！ | 橙红色大号字 |
| 5 | ⚡ 五杀！ | 金色超大号字 + 缩放脉冲 |
| 7+ | 👑 超神！ | 亮金色超大号字 + 缩放脉冲 + 画面轻微震动 |

连杀计数在整场战斗中累积（不按回合重置），战斗结束时清零。

**验收标准**：

| # | 标准 | WHEN / THEN |
|---|------|-------------|
| A4-1 | 三杀提示 | WHEN 同一场战斗中己方累计击杀第 3 个敌人 THEN 画布中央显示"🔥 三杀！"大号飘字 |
| A4-2 | 五杀提示 | WHEN 同一场战斗中己方累计击杀第 5 个敌人 THEN 画布中央显示"⚡ 五杀！"特大号飘字 |
| A4-3 | 超神提示 | WHEN 同一场战斗中己方累计击杀第 7 个及以上敌人 THEN 画布中央显示"👑 超神！"飘字并伴随画面轻微震动 |

## 3. 子功能 B：抽卡演出差异化

> 核心目标：根据武将品质（Q1-Q5）展示差异化的招募演出，品质越高仪式感越强。

### 3.1 现状分析

当前招募流程：
1. `RecruitManager.recruitSingle()` / `recruitTen()` 立即计算结果
2. 发射 `recruit:result` 事件（含 `results` 数组，每个元素有 `heroId, quality, isNew, template`）
3. `RecruitPanel._render()` 收到事件后直接用 `innerHTML` 渲染静态结果卡片
4. 同时 `CelebrationOverlay` 监听 `hero:added`，对 Q4+ 新武将弹出庆祝层

**问题**：
- 结果瞬间呈现，无"翻牌"或"揭晓"过程
- Q1-Q5 使用相同的渲染逻辑，差异仅为边框颜色
- `CelebrationOverlay` 的武将庆祝与招募面板的结果展示是两个独立流程，时序不协调
- 保底触发时无任何提示（玩家不知道这次是保底给的还是运气好）

### US-B1：品质分档演出

**作为**进行招募的玩家
**我想要**不同品质的武将有不同级别的登场仪式
**以便于**获得 Q5 武将时感受到与其稀有度匹配的"大事发生了"的兴奋感

**详细描述**：

招募结果不再由 `RecruitPanel._render()` 直接渲染，改为触发"演出序列"。演出使用 Modal 或 CelebrationOverlay 作为载体，分四档：

| 品质 | 演出级别 | 具体表现 |
|------|---------|---------|
| **Q1-Q2**（白/绿） | 轻量 | 快速翻牌效果（卡片从背面翻转到正面），无额外特效，0.5 秒完成 |
| **Q3**（蓝） | 标准 | 翻牌速度减慢 + 卡片边缘蓝色光芒边框脉冲，约 1 秒完成 |
| **Q4**（紫） | 隆重 | 黑屏过渡（0.5s 渐黑）→ 屏幕中央出现金色裂缝特效（CSS 动画，0.8s）→ 裂缝碎裂后显示武将全屏展示（emoji 放大 + 名称 + 称号）→ 底部展示武将专属对白（取自 `NpcDialogues.heroes[heroId].click` 池随机一条），总计约 3 秒 |
| **Q5**（橙） | 史诗 | 天道系统弹窗闪现"⚠ 检测到 SSR 异常"→ 屏幕产生"故障效果"（CSS glitch：色彩偏移 + 扫描线 + 画面抖动，1s）→ 故障消散 → 全屏武将展示（emoji 超大 + 名称 + 称号 + 品质光晕 + 飘散粒子/CSS 动画）→ 专属对白 → "天道系统：这位……我也没预料到。" 总计约 5 秒 |

**验收标准**：

| # | 标准 | WHEN / THEN |
|---|------|-------------|
| B1-1 | Q1-Q2 快速展示 | WHEN 招募到白色(Q1)或绿色(Q2)武将 THEN 结果以快速翻牌形式展示（≤0.5秒），无黑屏或特殊动画 |
| B1-2 | Q3 蓝光边框 | WHEN 招募到蓝色(Q3)武将 THEN 翻牌过程减速，卡片边缘出现蓝色脉冲光芒 |
| B1-3 | Q4 裂缝演出 | WHEN 招募到紫色(Q4)武将 THEN 展示黑屏→金色裂缝→全屏武将展示的完整演出序列，包含武将称号和专属对白 |
| B1-4 | Q5 故障演出 | WHEN 招募到橙色(Q5)武将 THEN 展示"天道系统异常检测"→屏幕故障效果→全屏武将展示的完整演出，包含粒子特效和专属对白 |
| B1-5 | 对白匹配人设 | WHEN 演出展示武将对白 THEN 对白内容与该武将的世界观人设一致（如诸葛亮说外卖相关的话、关羽说健身相关的话），来源于 `NpcDialogues` 数据 |

### US-B2：保底触发提示

**作为**抽卡触发保底机制的玩家
**我想要**知道这次高品质武将是保底机制给的
**以便于**理解保底系统在保护我，提升对抽卡系统的信任感

**详细描述**：

当 `RecruitManager._determineQuality()` 因保底计数器达到阈值（rare≥9、epic≥29、legendary≥79）而触发保底时，在演出中额外展示天道系统文案。

保底文案池（随机选一条）：
- "天道系统：概率保护机制激活。不用谢。"
- "天道系统：这次是系统罩你的，下次自己争气。"
- "天道系统：连续手气太差，触发了我的同情心模块。"

需要 `RecruitManager` 在 `recruit:result` 事件数据中新增 `isPityTriggered: boolean` 字段。

**验收标准**：

| # | 标准 | WHEN / THEN |
|---|------|-------------|
| B2-1 | 保底文案展示 | WHEN 保底机制触发（任意等级）THEN 演出中额外显示天道系统保底文案（带"天道系统"说话人标识） |
| B2-2 | 非保底无提示 | WHEN 正常概率抽中高品质武将（非保底触发）THEN 不显示保底文案 |

### US-B3：十连抽排序演出

**作为**进行十连抽的玩家
**我想要**十连结果按品质从低到高依次展示，最好的留到最后
**以便于**在翻牌过程中保持期待感，最后一张翻出高品质武将时获得最大惊喜

**详细描述**：

十连抽结果在展示前按品质升序排列。逐张展示：
- Q1-Q2 快速连翻（每张 0.3s）
- Q3 减速到 0.8s
- Q4/Q5 按各自的完整演出流程展示
- 全部展示完后，回到招募面板显示完整的十连结果网格（保留现有 `_renderResults` 的网格展示）

**验收标准**：

| # | 标准 | WHEN / THEN |
|---|------|-------------|
| B3-1 | 升序排列 | WHEN 进行十连抽 THEN 结果按品质从低到高依次展示，最高品质武将最后出现 |
| B3-2 | 低品质快翻 | WHEN 十连中展示 Q1-Q2 武将 THEN 快速翻过（每张 ≤ 0.3s），不拖延节奏 |
| B3-3 | 高品质完整演出 | WHEN 十连中包含 Q4/Q5 武将 THEN 该武将使用对应品质的完整演出流程（不因十连而缩减） |

### US-B4：跳过动画

**作为**多次抽卡的老玩家
**我想要**可以随时跳过当前的招募演出
**以便于**在不想等动画时快速看到结果

**详细描述**：

- 所有品质的演出中，玩家点击屏幕任意位置（或触摸任意位置）即可跳到当前演出的下一步
- 连续快速点击可跳过整个演出序列，直接进入结果总览
- 十连抽中点击跳过当前武将的演出，进入下一位武将的展示
- 跳过后所有结果仍然在面板中完整展示（不跳过数据，只跳过动画）

**验收标准**：

| # | 标准 | WHEN / THEN |
|---|------|-------------|
| B4-1 | 点击跳过 | WHEN 演出播放中玩家点击屏幕 THEN 立即跳过当前动画步骤进入下一步（或直接展示最终结果） |
| B4-2 | 数据完整 | WHEN 玩家跳过演出 THEN 招募面板仍完整展示所有招募结果（静态卡片网格）|
| B4-3 | 不阻塞游戏 | WHEN 演出播放期间 THEN `game:tick` 事件继续正常触发，挂机收益不中断 |

## 4. 子功能 C：离线收益趣味报告

> 核心目标：将干巴巴的离线收益数字，包装成一份武将"生活报告"，让每次回到游戏都有小惊喜。

### 4.1 现状分析

当前离线收益流程（`main.js` 第 117-203 行）：
1. 加载存档时计算离线时长，阈值 60 秒
2. `AdventureManager.calculateOfflineRewards(lastSaveTime)` 计算收益（金币、经验、木/石/铁，含效率折扣）
3. `ResourceManager.add()` 直接发放所有收益
4. 500ms 后弹出 Modal，标题"☀ 欢迎回来！"，内容为纯数字列表
5. 点击"收下！"仅关闭弹窗（收益已发放）

**问题**：
- 无动画过渡（突然弹窗）
- 收益在弹窗前已发放，"收下！"按钮无实际意义
- 无武将人格化描述，仅显示数字
- 缺乏与游戏世界观的情感连接

### US-C1：趣味化离线报告

**作为**离线一段时间后回到游戏的玩家
**我想要**看到一份武将们离线期间"干了什么"的趣味报告
**以便于**感觉武将是"活的"，有动力继续培养他们

**详细描述**：

报告内容分为两部分：
1. **武将活动描述**（趣味化）：根据队伍中的武将，从数据文件中随机选取匹配其人设的离线活动描述
2. **实际收益数字**（功能化）：底部展示真实的离线收益数据

武将活动描述应匹配其游戏内人设（参考 `NpcDialogues` 和 `HeroData` 中的 `title` 字段）。示例：

| 武将 | 人设 | 示例活动描述 |
|------|------|------------|
| 诸葛亮 | 外卖CEO | "优化了 3 条配送路线，差评率下降 0.02%" |
| 关羽 | 健身搭子 | "在训练场举铁 128 次，青龙偃月刀又重了 2 斤" |
| 赵云 | 瑜伽教练 | "巡逻了城墙 47 次，顺便教了守卫做拉伸" |
| 曹操 | 鞋业大亨 | "上架了 15 款新草鞋，其中 3 款还没拆包就卖光了" |
| 张飞 | 暴力教练 | "在校场吼了 200 声，隔壁两条街的猫都跑了" |
| 刘备 | 不情愿皇帝 | "签了 89 份奏折，哭了 3 次" |
| 吕布 | 奶茶店店长 | "调制了 42 杯'方天画戟特调'，好评率 99%" |
| 貂蝉 | 美妆博主 | "录了 2 条美妆教程，播放量突破天道服务器上限" |
| 孙权 | 直播达人 | "开了 5 场直播，喊了 178 次'家人们上链接'" |
| 司马懿 | 隐形创业者 | "在角落观察了所有人，笔记本又写满了一页" |

活动描述文案应存放在独立数据文件中，每位武将至少 5 条，数字部分可随机生成（与离线时长成比例缩放）。

**验收标准**：

| # | 标准 | WHEN / THEN |
|---|------|-------------|
| C1-1 | 触发条件 | WHEN 离线时间超过 5 分钟后打开游戏 THEN 弹出离线收益趣味报告弹窗 |
| C1-2 | 不触发条件 | WHEN 离线时间不足 5 分钟 THEN 不弹出报告，离线收益静默结算 |
| C1-3 | 武将活动描述 | WHEN 报告展示 THEN 包含当前队伍中每位武将的趣味活动描述（至少展示 1-3 位武将的活动），描述与该武将的游戏内人设匹配 |
| C1-4 | 实际收益展示 | WHEN 报告展示 THEN 底部清晰展示实际离线收益数字（金币、经验、各类资源） |
| C1-5 | 数字比例合理 | WHEN 活动描述中包含数字（如"巡逻了 N 次"）THEN 数字与离线时长成合理比例（离线越久数字越大），不会出现"离线5分钟巡逻了999次"的违和感 |

### US-C2：信封开启动画

**作为**回到游戏的玩家
**我想要**离线报告有一个"打开信封"的仪式化开场
**以便于**感受到"收到一封来信"的期待感

**详细描述**：

报告弹窗不直接展示内容，而是先呈现一个信封图案（可用 CSS + emoji 🧧/📨 实现），点击或自动播放后信封"打开"（CSS 翻转/展开动画），然后内容从信封中"展开"呈现。

信封封面文案（随机选一）：
- "📨 来自你的武将们的离线报告"
- "📨 武将日报 · 今日份"
- "📨 你不在的时候发生了这些事……"

报告标题："离线期间你的武将都做了什么？"

**验收标准**：

| # | 标准 | WHEN / THEN |
|---|------|-------------|
| C2-1 | 信封动画 | WHEN 离线报告触发 THEN 先展示信封封面（约1秒），随后信封打开展示报告内容，有可感知的动画过渡 |
| C2-2 | 标题展示 | WHEN 报告内容展开后 THEN 标题为"离线期间你的武将都做了什么？"或类似趣味化标题 |

### US-C3：延迟发放收益

**作为**查看离线报告的玩家
**我想要**点击"领取"按钮后才实际获得离线收益
**以便于**感觉这些收益是"我主动领取的奖励"而非被动获得

**详细描述**：

修改当前 `_showOfflineRewards()` 的流程：
- **当前**：先 `ResourceManager.add()` → 再弹窗 → "收下！"仅关闭弹窗
- **改为**：先弹窗展示报告 → 玩家点击"领取"按钮 → 触发 `ResourceManager.add()` 发放收益 → 关闭弹窗 → Toast 提示"已领取离线收益"

领取按钮文案（随机选一）：
- "📦 签收！"
- "🎁 全部收下！"
- "✅ 辛苦了，领取奖励"

如果玩家关闭弹窗而未点击领取（如点击背景关闭），收益仍然发放（防止丢失），但不触发额外 Toast。

**验收标准**：

| # | 标准 | WHEN / THEN |
|---|------|-------------|
| C3-1 | 点击领取发放 | WHEN 玩家在离线报告中点击"领取"按钮 THEN 实际发放离线收益（资源数字变化可见），弹窗关闭 |
| C3-2 | 收益不丢失 | WHEN 玩家以任何方式关闭报告弹窗（包括点击背景、点击关闭按钮）THEN 离线收益仍然发放（作为兜底） |
| C3-3 | 无重复发放 | WHEN 离线收益已发放 THEN 不会因任何原因重复发放同一笔离线收益 |

## 5. 范围排除（不做什么）

以下内容明确不在本 PRD 范围内，防止范围蔓延：

| 排除项 | 理由 |
|--------|------|
| **音效系统** | 当前项目无音频系统，本期不引入 |
| **战斗特效重制**（精灵动画/技能特效重做） | 飘字是轻量增强，不涉及精灵动画系统重构；特效重制需独立规划 |
| **抽卡概率调整** | 本 PRD 仅改变"展示方式"，不改变任何抽卡概率/保底数值 |
| **武将语音** | 纯前端项目，不引入音频资源；用文字对白替代 |
| **离线收益数值调整** | 不修改 `AdventureManager.calculateOfflineRewards` 的计算逻辑和效率参数 |
| **抽卡动画的 WebGL/3D 效果** | 坚持 CSS 动画 + Canvas 2D，不引入新渲染技术 |
| **战斗回放/录像** | 飘字是实时渲染，不涉及战斗录像功能 |
| **离线报告的社交分享** | 不做截图分享、好友对比等社交功能 |
| **武将立绘/头像系统** | 演出中使用现有 emoji 表情和文字，不引入图片立绘资源 |
| **新增后端服务** | 保持纯前端架构，不新增任何后端依赖 |

## 7. 技术约束与注意事项

> 以下为产品侧观察到的技术约束，供 `spec-architect` 设计技术方案时参考。

1. **Canvas 飘字系统已存在**：`battle-animations-canvas.js` 的 `_floatTexts` 数组 + `_drawFloatTexts()` 已有完整的飘字渲染管线（含描边、淡出），子功能 A 应在此基础上扩展而非另建系统

2. **EventBus 事件链**：战斗事件通过 `battle:tick` → `battle:log` → `BattleAnimations.playAttack/playSkill/playDeath` 传导，飘字增强应沿用此事件链

3. **招募事件数据**：`recruit:result` 事件已携带 `quality` 和 `template` 信息，演出逻辑需要的数据基本已在事件载荷中；但需新增 `isPityTriggered` 字段

4. **CelebrationOverlay 排队机制**：已有 `_enqueue` + `_showNext` 的队列展示机制，抽卡演出可考虑复用此排队模式

5. **离线收益发放时序**：当前在 `main.js` 第 163-167 行先发放、后弹窗；修改为延迟发放时需注意 `_maybeShowDailyLoginPopup()` 的等待逻辑（第 212-219 行检测 Modal 是否关闭）

6. **零依赖约束**：不可引入第三方动画库（如 GSAP、anime.js），所有动画用原生 CSS transitions/animations + Canvas 绘制实现

7. **localStorage 存储**：新增的武将活动文案数据文件不需要存储到 localStorage，作为静态数据加载即可

8. **移动端兼容**："点击跳过"需同时支持 `click` 和 `touchstart` 事件

9. **纯前端实现**：无构建工具，所有新文件需手动添加到 `index.html` 的 `<script>` 标签

## 8. 优先级与实施建议

| 优先级 | 子功能 | 理由 |
|--------|--------|------|
| 🔴 P0 | 子功能 A：战斗飘字系统增强 | 最高频场景（每次战斗都触发），且现有基础设施完善（仅需扩展），实施成本最低、收益最高 |
| 🟡 P1 | 子功能 B：抽卡演出差异化 | 中频场景但情绪峰值最高（Q5 演出是玩家最兴奋的时刻），需要较多 CSS 动画工作 |
| 🟢 P2 | 子功能 C：离线收益趣味报告 | 低频场景（每日 1-3 次），需要新增活动文案数据，但不影响核心循环 |

**建议实施顺序**：A → B → C

每个子功能可独立交付和验收，互相之间无硬依赖。
